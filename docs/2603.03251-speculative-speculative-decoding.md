# 推测性推测解码（Speculative Speculative Decoding）

## 1. 基本情况

- 题目（中 / 英）：推测性推测解码 / Speculative Speculative Decoding
- 作者：Tanishq Kumar, Tri Dao, Avner May
- 单位：Department of Computer Science, Stanford University; Department of Computer Science, Princeton University; Together AI
- arXiv 编号：2603.03251
- 提交日期：2026-03-03 UTC（v1）；arXiv 页面显示 last revised 2026-05-04（v3）
- arXiv 链接：https://arxiv.org/abs/2603.03251
- PDF 链接：https://arxiv.org/pdf/2603.03251

- 领域与备注：cs.LG；ICLR 2026

## 2. 核心贡献概述

- 中文版：本文提出 speculative speculative decoding（SSD），把普通 speculative decoding 中“先 draft、再 verify、再继续 draft”的串行依赖进一步并行化：target model 验证上一轮 speculation 时，draft model 预判可能的 verification outcomes，并提前为这些结果生成下一轮 speculation。作者将该框架优化成 Saguaro，通过 outcome cache、geometric fan-out、cache-aware sampling 和 batch-aware fallback，使 Llama/Qwen 推理在多个任务上快于强 speculative decoding baseline。
- English version（摘自 abstract / introduction）：Abstract 中的核心表述是：“If the actual verification outcome is in the predicted set, a speculation can be returned immediately.” Introduction 进一步总结 Saguaro “is on average 30% faster than the strongest speculative decoding baselines and up to 5x faster than autoregressive generation.”

## 3. 一句话精髓（写给外行）

如果普通 speculative decoding 像让小助手先写草稿再等老师批改，SSD 就是在老师批改时让小助手预演几种可能的批改结果，并把每种结果后的下一页都先写好。

## 4. 学术贡献清单

### 4.1 动机的发现与阐明

作者指出，ordinary speculative decoding 虽然把 target model 的多个 token 验证合成一次并行 forward pass，但它自身仍有一个串行气泡：draft model 必须等 verifier 返回 accepted length 和 bonus token 后，才能知道下一轮从哪个 prefix 继续 speculation。这个瓶颈在 low-latency、small batch 推理中尤其明显，因为 draft latency 会进入 critical path。

论文把这个瓶颈重写成一个 verification outcome prediction 问题。一次验证结果不是只有“接受几个 token”，还包含 residual distribution 或 target distribution 采出的 bonus token，因此 outcome 空间约为 $(K+1)V$。这解释了为什么简单地“异步跑 draft”不够：若只赌所有 token 都被接受，或只在 cache miss 后 just-in-time speculation，较高 temperature、较大 batch 或较低 acceptance 的场景很快会失效。

### 4.2 方法的创新

- 提出 SSD framework：target verifier 与 draft speculator 分别在不同硬件上并行执行，draft 在 verifier 运行时预测下一轮可能 prefix，并在 speculation cache 中准备好对应 token 和 logits。
- 提出 Saguaro cache construction：在有限 cache budget $B$ 下选择每个 accepted length $k$ 的 fan-out $F_k$，理论上得到 capped geometric fan-out，而不是 naive uniform fan-out。
- 提出 Saguaro sampling：通过下调 cached top-$F$ draft tokens 的采样概率，把 residual distribution 的质量推向 cache 中的 token，从而提高 bonus token 命中 cache 的概率。
- 提出 Saguaro fallback：根据 batch size 在 slow but accurate neural backup 与 low-latency backup（实现中为 random tokens，可替换为 n-gram / Infini-gram 等非神经 speculator）之间切换。
- 系统实现层面：用 custom PyTorch inference engine、PagedAttention、continuous batching、TP、BF16、torch compilation、CUDAGraphs、NCCL 和 custom sparse attention mask，让 draft cache 的大量分支在单独 H100 上并行生成，同时不向 target 传输 draft KV cache。

### 4.3 实验上的核心结论

作者在 Llama-3.1-70B / Llama-3.2-1B draft 和 Qwen3-32B / Qwen3-0.6B draft 上评测 HumanEval、GSM8K、Alpaca、UltraFeedback。附录数值显示，Llama 系列平均 decode throughput 为 AR 54.7 tok/s、SD 161.8 tok/s、SSD 255.8 tok/s，即 SSD/SD 为 $1.58\times$，SSD/AR 为 $4.68\times$；Qwen 系列平均 SSD/SD 为 $1.49\times$，SSD/AR 为 $2.29\times$。主文图还显示 SSD 推动 throughput-latency Pareto frontier，特别是在 small batch 下收益最大。

## 5. 写作故事线

论文的叙事从一个很窄但关键的系统瓶颈出发：autoregressive decoding 是串行的，speculative decoding 已经把 target 验证并行化，但 draft 和 verification 之间仍然互相等待。Introduction 先用 Figure 1 把普通 SD 的 idle draft gap 和 SSD 的 async pre-speculation 对比出来，再提出三个挑战：如何预测 verification outcome、如何在 cache hit rate 与 acceptance rate 之间折中、cache miss 后如何 fallback。

接着，Background 复述 speculative decoding 的 lossless accept/reject 机制、acceptance rate 公式和 residual distribution，并把 prior work 分成 parallel SD、tree-based SD、improved draft architectures 三条线。这个安排很重要：作者先承认已有异步和 tree 方向，再把本文的问题界定为“预测 verification outcome 并为 outcome 建 cache”，从而和 AMUSD/PEARL/SwiftSpec/SpecBranch 等工作区分。

第 3 节给出 SSD framework 和 speedup bounds，完成理论抽象：只要 cache hit 发生，下一轮 draft latency 就被 verifier latency 遮住；若 miss，则退回 backup。第 4 节 Saguaro 按三个挑战拆解：cache topology 用 geometric fan-out；sampling 通过操控 residual distribution 增大 hit；fallback 用 batch-size threshold 避免整批等待 slow backup。第 5 节再用 end-to-end evaluation 证明这些局部优化叠加后，不只是 microbenchmark 变好，而是能在真实 serving engine 设定下超过 SD 与 open-source engines。

![Figure 1: SSD high-level comparison and end-to-end speed](sources/2603.03251-speculative-speculative-decoding/arxiv/figures/ssd_fig1.pdf)

图解：左侧说明普通 SD 的 verifier 验证完成后，仍要等待 draft 生成下一段 speculation；中间展示 SSD 在 verifier 工作时用独立 draft 设备提前生成多条可能后续。右侧给出 Llama-3.1-70B、batch size 1、greedy decoding 的概览结果，SSD 的平均 decode tok/s 约为 AR 的 4 倍、SD 的 1.3 倍左右。这张图承担了论文的“故事入口”：它不是改变 target distribution，而是把 draft overhead 从 critical path 中拿走。

## 7. 批判性分析

从外部文献看，SSD 的“异步化 drafting 与 verification”不是凭空出现的方向。AMUSD（arXiv:2410.17375）已经把 draft 和 verify phase 解耦到多个设备上，PEARL（arXiv:2408.11850）也直接把 mutual waiting problem 作为动机，并用 pre-verify / post-verify 让 draft 与 verification 有重叠。SSD 的新意在于把“下一轮 prefix 不确定”明确建模为 verification outcome cache：outcome 包含 accepted length 与 bonus token，Saguaro 不只准备 all-accepted path，而是按概率和资源预算为多个 outcome 预生成 speculation。

与 SwiftSpec（arXiv:2506.11309）和 SpecBranch（arXiv:2506.01979）的关系更微妙。SwiftSpec 同样把 speculative decoding 做成 asynchronous / disaggregated pipeline，并通过 parallel tree generation 和 KV-cache engineering 降低低延迟场景的 draft overhead；SpecBranch 也用 branch parallelism 预先 hedge likely rejections。Saguaro 相比二者的区别主要在三点：一是 outcome 定义包含 bonus token，因此 cache key 更贴近 exact speculative sampling；二是 fan-out allocation 有 geometric optimality 分析；三是加入 cache-aware sampling，主动改变 draft distribution 来控制 residual distribution。换言之，Saguaro 更像是对 asynchronous branch-parallel SD 的系统化和概率化版本，而不是“首次打破串行屏障”的孤立发明。

Mirror-SD（arXiv:2510.13161）进一步说明这一方向在 2025 年已有多个并行探索：它用 heterogeneous accelerator 上的 branch-complete rollouts 和 speculative streaming 降低 draft latency。SSD 与 Mirror-SD 的相似处是都把 draft/target 的等待气泡视为核心敌人；差异在于 SSD 保持 target verifier 只验证一条普通 speculation，不让 target 额外验证大树，而是把额外 compute 放到 draft-side cache。

agent 评论：本文最脆弱的 claim 是“strongest speculative decoding baselines”和“up to 5x”的外推范围。附录的主要 end-to-end 数值是 single node H100、decode-only、512 prompts、batch size 1 或少量 batch sweep；SSD 还额外使用 1 张 H100 draft GPU，而 AR/SD baseline 多为 4 张 H100 target TP。作者确实给了 throughput-latency Pareto / tok/s/GPU 视角，但读者仍应把结论理解为“在低延迟、draft device 可独占或可 disaggregate 的 serving 场景下非常强”，而不是所有吞吐型 workload 的无条件胜利。

agent 评论：第二个脆弱点是 cache hit 的经验幂律与 sampling trade-off。Theorem 里的 geometric fan-out 依赖 $r$ power-law cache hit rate 假设，实验在 Llama/Qwen 与四个数据集上支持，但不同 draft-target pair、top-p/top-k sampling、long context、工具调用或多轮 chat 分布是否仍保持类似曲线，需要更多证据。Saguaro sampling 通过牺牲 acceptance rate 换 cache hit rate，这个 trade-off 在图中成立，但最优 $C$ 仍是经验超参，且可能与 temperature、domain、draft quality 强耦合。

![Figure: EAGLE-3 vs SSD-EAGLE-3 conditioning](sources/2603.03251-speculative-speculative-decoding/arxiv/figures/eagle3-figure.pdf)

图解：这张附录图解释 SSD 与 EAGLE-3 组合时的一个隐含代价：标准 EAGLE-3 可以用上一轮 target activations 条件化，而 SSD 因为提前开始下一轮 speculation，需要用更多 draft self-activations 代替尚未产生的 target activations。它支持作者“SSD 可组合 EAGLE-3，但不是免费组合”的判断。读者应关注这里的限制：越长 lookahead 越可能降低 EAGLE-style draft 的 acceptance。

## 8. 方法细节

### 算法流程

普通 speculative decoding 在每轮先用 draft model 生成 $K$ 个 token，然后 target model 一次 forward 并行验证这些 token。SSD 把 speculator 与 verifier 放到不同硬件上，让二者异步循环：

1. speculator 先生成当前轮 $spec\_tokens$ 并发给 verifier。
2. verifier 对 $spec\_tokens$ 做标准 SD verification，得到 $verify\_outcome=(k,t^*)$，其中 $k$ 是 accepted length，$t^*$ 是 bonus token。
3. verifier 正在验证时，speculator 预测多个可能的 $verify\_outcome$，并为每个 outcome 预先生成下一轮 speculation，写入 speculation cache。
4. verifier 返回真实 outcome 后，若 outcome 命中 cache，speculator 立即返回对应 tokens 与 logits；若 miss，则调用 fallback speculator。
5. verifier 仍执行标准 speculative verification，因此输出分布保持 target model 的分布不变；SSD 只改变 draft-side timing 与 cache construction。

![Figure: speculation cache topology](sources/2603.03251-speculative-speculative-decoding/arxiv/figures/fan_out_simple_1.pdf)

图解：该图把 speculation cache 画成从当前正在验证的 sequence trunk 出发的多条候选后续。$F_0,F_1,\ldots$ 表示不同 accepted length 下为 bonus token 预留的猜测数量。它说明 Saguaro 的核心不是验证整棵树，而是为“验证后会落到哪个 prefix”提前准备下一轮线性 speculation。

### 关键公式

普通 SD 的 acceptance rate 由 draft 与 target 分布距离决定：

$$
\alpha = \sum_x \min\{p_{\mathrm{target}}(x),\,p_{\mathrm{draft}}(x)\} = 1 - \tfrac{1}{2}\lVert p_{\mathrm{target}} - p_{\mathrm{draft}} \rVert_1
$$

第一次 rejection 后的 bonus token 来自 residual distribution：

$$
r(\cdot) \propto \max\left(p_{\mathrm{target}}(\cdot)-p_{\mathrm{draft}}(\cdot), 0\right)
$$

SSD 相对 autoregressive decoding 的 expected speedup 为：

$$
speedup_{\mathrm{SSD}} =
\frac{p_{\mathrm{hit}} \cdot E_{\mathrm{hit}} + (1-p_{\mathrm{hit}}) \cdot E_{\mathrm{miss}}}{p_{\mathrm{hit}} \cdot \max(1, T_p) + (1-p_{\mathrm{hit}}) \cdot (1 + T_b)}.
$$

其中 $T_p,T_b$ 是 primary / backup speculator 相对 verifier 的 latency，$E_{\mathrm{hit}},E_{\mathrm{miss}}$ 是 cache hit / miss 后期望生成 token 数。若 primary draft 能在 verifier 完成前结束，cache hit 会把 draft latency 从 denominator 中隐藏掉。

Saguaro cache topology 的优化结果是 capped geometric fan-out。若 primary speculator acceptance rate 为 $a_p$，并具有 $r$ power-law cache hit rate，则：

$$
F_k = F_0 \cdot a_p^{k/(1 + r)}  \;\; \forall k < K,
$$

$$
F_K = F_0 \cdot a_p^{K/(1 + r)} \cdot (1-a_p)^{-1/(1 + r)}.
$$

直觉是 accepted length 遵循截断几何分布：越不可能出现的 accepted length，越不该分配过多 bonus-token guesses。

Saguaro sampling 用超参 $C\in[0,1]$ 下调 cache token 的 draft 概率：

$$
\sigma_{F,C}(z) \propto  \begin{cases}
C\cdot \exp\Big(z_t\Big)& \text{if } t \in \text{top}_F(z) \\
\exp\Big(z_t\Big)& \text{otherwise.}
\end{cases}
$$

由于 residual mass 与 $p_{\mathrm{target}}(t)-p_{\mathrm{draft}}(t)$ 的正部有关，降低 top-$F$ cached tokens 的 draft probability 会把 bonus token 的 residual mass 推向 cache，从而提高 cache hit；代价是 draft distribution 离 target 更远，acceptance rate 可能下降。

![Figure: cache hit rate scaling with fan-out](sources/2603.03251-speculative-speculative-decoding/arxiv/figures/dts_analysis_final.pdf)

图解：左右两个 rejection-rate 图显示，当 fan-out $F$ 从 2 增大到 128，cache miss/rejection rate 近似按 log-log 直线下降，这支撑了 power-law cache hit 假设。右图显示 overall $p_{\mathrm{hit}}(F)$ 随 $F$ 单调提高，温度越高通常越难命中。该图是 geometric fan-out 分析和“更多 draft compute 可换 cache hit”的经验基础。

![Figure: Saguaro sampling trade-off](sources/2603.03251-speculative-speculative-decoding/arxiv/figures/unified_cache_hit_and_saguaro_plots.pdf)

图解：左图展示 $C$ 从 1 降到 0 时，cache hit rate 上升但 acceptance rate 下降，说明 Saguaro sampling 在两个目标之间做显式折中。右侧 toy schematic 解释了机制：downweight cached top tokens 后，residual distribution 从非 cache tokens 转向 cache tokens。读者应注意，这不是提升 draft quality，而是有意改变 draft sampling 来让 verifier 的 bonus token 更可预测。

### 所用模型 / backbone / 数据流

- Llama 主实验：target 为 Llama-3.1-Instruct 70B，draft 为 Llama-3.2-1B-Instruct。
- Qwen 附录实验：target 为 Qwen3-32B，draft 为 Qwen3-0.6B；部分 cache scaling 图还比较 0.6B 与 1.7B draft。
- AR / SD baseline：target model 以 tensor parallelism 跑在 $4\times$H100 80GB；SD draft 与 target collocated。
- SSD：target 仍为 $4\times$H100，draft 额外跑在独立 $1\times$H100 上，draft 与 target 每轮通过 NCCL 通信。
- 通信内容：target 向 draft 发送 sequence ID、accepted-prefix length、recovery/bonus token、sequence lengths、draft block tables 和 temperature；draft 返回 cache-hit bitmap、每个 sequence 的 $K$ speculative tokens 和 $K$-step logits。论文明确说不传输 KV cache。

![Figure: custom SSD attention mask](sources/2603.03251-speculative-speculative-decoding/arxiv/figures/custom_mask_visualization.pdf)

图解：该图展示 $B=1,K=3,F=4,i=2$ 时的 custom sparse attention mask。黑色区域表示可 attend 的位置：左侧 prefix mask 对应 verified prefix，中间的斜带让每个 branch 只 attend 自己的 fork path。它揭示了 Saguaro 的系统难点：多 outcome speculation 不是简单 batch expand，还涉及复杂的 KV page 与 sparse attention 访问模式。

### 算力资源需求

论文没有训练新模型，因此主要算力是推理评测与系统实验。作者明确给出的资源是：所有实验在单个 NVIDIA H100 节点上完成；AR/SD 每次使用 TP=4，即 $4\times$H100 80GB；SSD 使用 TP=4 target 加 $1\times$H100 draft，即一次最多 5 张 H100。默认设置是 batch size 1、greedy decoding、decode throughput 不含 prefill；每个数据集取 128 prompts，每个 prompt 生成 512 decode tokens，四个数据集合计 512 prompts / 262,144 decode tokens。

估算：按附录表的 Llama 平均 throughput，完整 262,144-token decode sweep 的墙钟时间约为：AR $262144/54.7 \approx 79.9$ 分钟，SD $262144/161.8 \approx 27.0$ 分钟，SSD $262144/255.8 \approx 17.1$ 分钟。Qwen SSD 平均 203.8 tok/s，对应约 21.4 分钟。真实总实验时间会更高，因为还包括 prefill、warmup、baseline sweeps、batch sweeps、不同 temperatures、不同 fan-out、Qwen/Llama 多组图和失败配置重跑。

算力开销方面，附录写明 SSD 的 draft 每轮解码 $BK(K+1)F$ 个 token，而普通 SD draft 每轮为 $BK$ 个 token；若 $\hat{c}$ 是 draft forward pass 相对 target FLOPs 的单位 compute，则 draft-side 额外 FLOPs 因子为 $\hat{c}(K+1)F$。speculation cache 需要存储 $O(BFK(K+1)(V+1))$ bits，实践中约为 hundreds of MB；NCCL 通信是每轮 target-to-draft $O(B)$ outcome 信息和 draft-to-target $O(BKV)$ tokens/logits，作者称 NVLink 下不是瓶颈。

## 9. 实验

### 9.1 评测数据集

- HumanEval：代码生成任务，用来测试结构化、可预测性较强的 code decoding 场景。
- GSM8K：数学 word problems，用来测试推理/数学文本生成。
- Alpaca：instruction-following prompts，用来测试一般指令响应。
- UltraFeedback：chat / feedback 风格数据，用来测试更开放的对话式生成。

实验抽样为每个数据集 128 prompts，每个 prompt 生成 512 decode tokens；四个数据集合计 512 prompts。论文使用 vanilla sampling，不使用 top-p 或 top-k；主文默认 batch size 1、greedy decoding，另有 temperature 与 batch-size sweep。

### 9.2 评测指标

- Decode throughput（tok/s）：每秒 decode tokens 数，不含 prefill。主结果直接用它比较 AR、SD、SSD 和 open-source engines。
- Speedup ratio：包括 SSD/SD 与 SSD/AR，说明相对普通 speculative decoding 和 autoregressive decoding 的倍率。
- Cache hit rate $p_{\mathrm{hit}}$：verification outcome 是否命中 draft 预先构造的 speculation cache，是 SSD 是否能隐藏 draft latency 的核心指标。
- Acceptance rate $\alpha$：普通 SD 和 SSD 中 draft token 被 verifier 接受的概率，决定每轮平均产出 token 数。
- Throughput-latency Pareto：以 tok/s/GPU 与 per-sequence latency inverse 展示不同 batch size 下的 device-normalized trade-off。

### 9.4 消融实验

**Cache topology / geometric fan-out。** 作者比较 uniform fan-out 与 theorem-derived geometric fan-out。在 Llama 和 Qwen 上，geometric fan-out 在 temperature 提高时尤其有用，因为 outcome 分布更分散，uniform allocation 更容易把 budget 浪费在低概率 accepted length 上。

![Figure: Llama temperature and fan-out ablation](sources/2603.03251-speculative-speculative-decoding/arxiv/figures/temp_fan_out_llama.pdf)

图解：左图显示在 temperature 0 到 1.0 下，SSD 均快于 SD；geometric fan-out 相比 uniform 的优势在高温时更明显。右图显示 cache hit rate 随 temperature 升高下降，但 geometric fan-out 始终提高 hit。它直接支撑“cache topology 不是装饰性优化，而是高温下维持 SSD 的关键”这一点。

![Figure: Qwen temperature and fan-out ablation](sources/2603.03251-speculative-speculative-decoding/arxiv/figures/temp_fan_out_qwen.pdf)

图解：Qwen 的 temperature sweep 走向与 Llama 类似，但整体速度和 hit rate 水平不同。geometric fan-out 对 Qwen 的绝对提升较温和，却仍在 temperature 1.0 下拉开更明显差距。该图说明 Saguaro 的 fan-out 策略不是只针对 Llama 调出来的，但不同模型族仍需重新调参。

**Batch-size fallback。** 作者比较 fast backup、neural backup 和 sync baseline，并给出 batch 16 下增加 draft GPUs 的 forecast。

![Figure: batch scaling and fallback](sources/2603.03251-speculative-speculative-decoding/arxiv/figures/batch_scaling_march2.pdf)

图解：左图显示 batch size 为 1 时 neural backup 更强，但 batch size 增大后 fast backup 反而更优，因为只要 batch 中任一元素 cache miss，整批都要等 backup。右图说明增加 draft GPUs / fan-out 可以在 batch 16 下继续提高 decode tok/s，但提升已开始接近 compute-bound 形态。这个消融支撑 Saguaro fallback theorem，也暴露了 SSD 在大 batch 下对 draft compute 的强依赖。

**Baseline sweeps。** 附录对 SGLang EAGLE-3、SGLang standalone SD 和 vLLM 进行了 lookahead / topk sweep。SGLang standalone 的最佳 Llama 结果约 201.9 tok/s，SGLang EAGLE-3 最佳约 192.8 tok/s，vLLM EAGLE-3 最佳约 197.6 tok/s；这解释了为什么主文把 SGLang SD 作为 strongest open-source inference engine baseline。若只看作者自研 SD baseline，Llama 平均为 161.8 tok/s；若看 sweep 中最好单配置，open-source SD baseline 会更强，但 SSD 平均 255.8 tok/s 仍明显领先。

### 9.5 结果分析

作者认为：SSD 的主要收益来自隐藏 draft latency，而不是让 target verifier 一次验证更多 target-side token tree。cache hit rate 越高，draft overhead 越容易完全消失；fan-out 增大可提升 hit，但也增加 draft-side compute，因此 Saguaro 必须优化 fan-out shape 和 fallback。作者还认为 SSD 不仅降低 latency，也推动 throughput-latency Pareto frontier，说明额外 device 的使用在低 batch 场景下是划算的。

作者认为：Saguaro sampling 解决了一个普通 SD 没有的问题，即 bonus token 的 residual distribution 难预测。通过主动改变 draft sampling，让 cached top tokens 成为 residual distribution 的高概率区域，可以提高 hit rate；但 acceptance rate 会下降，所以最优 $C$ 取决于 temperature、draft quality 与 cache budget。

agent 认为：实验最有说服力的是 Llama/Qwen 两个模型族、四个数据集、open-source engine sweep 与系统实现细节的组合，而不是单个 speedup 数字。尤其是 decode-only 设置、extra draft GPU、batch size 1 默认条件，使得结论应被理解为低延迟 serving 优化：当用户愿意用额外 H100 或集群级 draft endpoint 换 latency 时，SSD 很有吸引力；当 workload 已经 throughput-bound 或 batch 很大时，收益会被 cache miss 和 draft compute 压缩。

agent 认为：Saguaro 的失败模式也比较明确。第一，cache hit 不足时，SSD 会退回 backup，低 batch 下可用 neural backup 保质量和速度，大 batch 下只能用 fast backup 保 latency，但这会降低 $E_{\mathrm{miss}}$。第二，custom sparse attention mask、KV page rollback、NCCL fused payload 都增加系统复杂度，论文虽然说 communication 不是瓶颈，但实现 bug 和数值一致性风险需要代码层面验证。第三，top-p/top-k、长上下文、服务端多租户和真实 prompt length 分布没有被充分覆盖，后续系统部署还需要更广的 workload study。

## 10. 代码实现观察

### 10.1 仓库基本情况

- 仓库地址：https://github.com/tanishqkumar/ssd；本地浅克隆 commit 为 `d7eb8fa`。
- License：MIT。`LICENSE` 与 `pyproject.toml` 都标注 MIT，代码可在 MIT 条款下复用。
- 仓库不含模型权重或预处理数据。本地代码目录约 1.2 MB，未找到 `.safetensors`、`.bin`、`.pt`、`.pth`、`.ckpt` 权重文件；README 要求通过 HuggingFace cache 和脚本自行准备模型、数据。
- 环境假设很具体：Python 3.11+、CUDA >= 12.8，README 明确说代码在 H100 上编写和测试；`pyproject.toml` 固定 `torch==2.8.0`、`triton==3.4.0`、`flashinfer-python==0.5.2`、`sgl-kernel==0.3.17.post1`、`nvidia-cutlass-dsl==4.2.1` 等依赖。没有 Dockerfile、CI 配置或 `requirements.txt`。
- 模型和数据路径通过环境变量强绑定：`SSD_HF_CACHE` 必须指向 HuggingFace hub 目录，`SSD_DATASET_DIR` 必须指向已处理数据目录，`SSD_CUDA_ARCH` 默认是 `9.0`。`ssd/paths.py:19-55` 在 import 时就会检查缺失环境变量，因此普通脚本运行前必须先设置路径。

### 10.2 方法实现核对

- 与论文一致：async SSD 确实把 target TP ranks 和 draft runner 分成不同进程。`ssd/engine/llm_engine.py:61-93` 中，async 模式下 `num_tp_gpus = num_gpus - 1`，最后一个 rank 启动 `DraftRunner`，rank 0 启动 target `ModelRunner` 并通过 NCCL process group 与 draft 通信。`ssd/engine/model_runner.py:98-107` 使用 `dist.init_process_group("nccl", ...)`，`ssd/engine/model_runner.py:258-259` 为 target rank 0 与 draft rank 单独建 `async_pg`。
- 与论文一致：target 到 draft 的请求 payload 是 verification outcome key 与 KV 地址元数据，而不是 KV cache 本体。`ssd/engine/speculator_async.py:136-156` 发送 `(seq_id, accepted_len-1, recovery_token)`、sequence length、draft block table 和 temperature；`ssd/engine/speculator_async.py:181-185` 接收 cache-hit bitmap、$K$ 个 speculative tokens 和 $K$ 步 logits。draft 侧在 `ssd/engine/draft_runner.py:299-310` 解包同一 payload，在 `ssd/engine/draft_runner.py:360-362` 返回 fused hit/tokens 与 logits。

文件 `ssd/engine/speculator_async.py:136-156` 的关键逻辑如下：

```python
self._cache_keys[i, 0] = seq.seq_id
self._cache_keys[i, 1] = seq.last_spec_step_accepted_len - 1
self._cache_keys[i, 2] = seq.recovery_token_id
send_int64(self.async_pg, self.draft_runner_rank,
           self._cache_keys, self._num_tokens_buf,
           self._block_tables_buf.to(torch.int64), temps_as_int64)
```

- 与论文一致：cache key 就是论文中的 verification outcome 近似实现。draft cache 的 key 在 `ssd/engine/draft_runner.py:824-830` 被构造成 `[seq_id, k_idx, rec_token]`，对应 sequence、accepted length 分支和 bonus/recovery token；命中时返回该 key 下预生成的 tokens/logits。
- 与论文一致：standard speculative verification 被保留。`ssd/utils/verify.py:55-63` 只在 temperature 非零且 cache hit，或 JIT backup 真实跑了 draft 时，才走 $p/q$ ratio acceptance；非 JIT 的 cache miss 不会把随机 fast fallback 当作 draft distribution，而是回退到 target 分布采 recovery token。这一点补足了论文没有展开的 exactness 保护。

文件 `ssd/utils/verify.py:55-63`：

```python
base_ratio_rows = ((temps_t > 0) | (temps_q > 0))
if jit_speculate:
    ratio_rows = base_ratio_rows
else:
    ratio_rows = base_ratio_rows & (cache_hits.to(torch.bool)
                                    if cache_hits is not None
                                    else torch.zeros_like(base_ratio_rows, dtype=torch.bool))
```

- 与论文一致：PagedAttention / KV addressing 落在 `block_table` 与 FlashInfer paged KV wrapper 上。`ssd/layers/attention.py:105-130` 使用 `flash_attn_with_kvcache(..., page_table=context.block_tables, ...)`；async tree decode 则在 `ssd/engine/model_runner.py:159-205` 初始化 `flashinfer.BatchPrefillWithPagedKVCacheWrapper`，并为 CUDA graph 模式预分配 `custom_mask_buf`、`paged_kv_indices_buf` 等 buffer。
- 与论文一致：custom sparse attention mask 有独立实现。`ssd/engine/helpers/mask_helpers.py:24-48` 预计算 prefix mask、glue/recovery causal mask 和 per-step diagonal mask；`ssd/engine/helpers/cudagraph_helpers.py:266-313` 在 step 0 用 CPU/Numpy 预打包所有 $K$ 步 masks，再复制到 FlashInfer wrapper buffer，减少逐步 GPU mask 构造和 CPU sync。
- 与论文一致：fanout `f` 和 lookahead `k` 是公开 CLI 参数。`bench/bench.py:34-40` 默认 sync `k=6`、async `f=3`，README 的 SSD 主命令为 `--gpus 5 --spec --async --k 7 --f 3`。`ssd/config.py:64-70` 会把单个 `f` 展开成长度 `K+1` 的 `fan_out_list`。
- 与论文不一致：未发现会推翻论文主体算法或第 8/9 节实验设置的硬性不一致。
- 需要限定理解：代码默认 `--f 3` 并不会自动按论文公式计算 capped geometric fan-out，而是生成均匀 `fan_out_list=[3]*(K+1)`；若要复现实验里的 geometric / hit-miss fanout，需要通过 `--flh`、`--flm` 显式传每个 accepted length 的 fanout。`bench/bench.py:37-39` 暴露这些参数，`ssd/utils/async_helpers/async_spec_helpers.py:57-75` 按 hit/miss 选择对应 per-depth counts。
- 需要限定理解：Saguaro sampling 在代码中由 `--x` / `sampler_x` 开启。`ssd/layers/sampler.py:40-50` 和 `ssd/utils/async_helpers/async_spec_helpers.py:81-104` 对 top-$F$ probability 乘 `sampler_x` 后重归一化；README 的主 benchmark 命令是 greedy `--temp 0`，未传 `--x`，因此该命令主要验证 async cache/fanout 路径，不触发 sampling trade-off。
- 论文未提及但代码中存在的工程细节：默认 backup 是 `--backup jit`，即 cache miss 时 draft 侧即时跑神经 draft；`--backup fast` 时 `ssd/engine/draft_runner.py:192-195` 用随机 logits/token 初始化 miss slots，然后 verifier 对 miss 行直接按 target 分布恢复，避免等待神经 backup。EAGLE3 路径还要求 `jit_speculate=True`，见 `ssd/engine/draft_runner.py:40-42`。
- 论文未提及但代码中存在的工程细节：大量使用 CUDA graphs。`ssd/engine/model_runner.py:278-302` 捕获 decode、verify、FI tree decode、EAGLE glue decode；`bench/bench.py:28` 的 `--eager` 用于关闭 CUDA graphs，README 明确建议总是用 `python -O` 关闭 debug overhead。
- 论文未提及但代码中存在的工程细节：FlashInfer 0.5.2 有本地 monkey patch。`ssd/layers/sampler.py:7-21` 修补 `flashinfer.sampling.get_seed_and_offset` 的 CUDA generator state 问题，并在 `ssd/layers/sampler.py:23-36` 固定 `torch.manual_seed(0)` 和 sampler generator seed。
- 论文未提及但代码中存在的工程细节：prefix caching 不是所有路径都同等启用。`ssd/engine/model_runner.py:506-516` 的通用 prefill 支持 prefix cache block tables；但 async draft prefill 在 `ssd/engine/draft_runner.py:83-91` 没把 `block_tables` 传入 context，代码注释写明这“essentially removes prefix caching”。因此 README 中的 prefix caching 支持应理解为 engine 支持，而非 async draft prefill 全路径无条件启用。
- 论文未提及但代码中存在的工程细节：外部 baseline 需要分环境运行。`bench/README.md` 要求 SSD、SGLang 0.5.9、vLLM 0.16.0 使用不同环境，因为 FlashInfer 版本冲突；SGLang/vLLM benchmark 走 server API，并承认包含 HTTP overhead 和 prefill time，但认为 512 output tokens 下影响可忽略。

### 10.3 真实算力规模

- 官方 README 命令确认主路径与报告第 8/9 节一致：AR 使用 Llama 70B、`--gpus 4 --b 1 --temp 0 --numseqs 128 --output_len 512 --all`；sync SD 使用 `--gpus 4 --spec --k 6`；SSD 使用 `--gpus 5 --spec --async --k 7 --f 3`。`--all` 在 `bench/bench_helpers.py:196-222` 中展开为 HumanEval、Alpaca、GSM8K、UltraFeedback 四个数据集，每个 `numseqs` 条，所以默认是 $128\times4=512$ prompts。
- Qwen 路径由同一个 benchmark 脚本支持，使用 `--qwen --size 32`，draft 默认映射到 Qwen3-0.6B。`bench/bench_helpers.py:113-128` 映射 Qwen3-32B target 与 Qwen3-0.6B draft；`bench/bench_helpers.py:96-112` 映射 Llama target，其中 native SSD 的 `--llama --size 70` 默认是 Llama-3.1-70B-Instruct。
- 并行度：`ssd/config.py:55` 断言 `1 <= num_gpus <= 8`，代码只覆盖单节点；async SSD 中 target TP size 是 `num_gpus-1`，draft 固定单卡，见 `ssd/engine/llm_engine.py:61-93` 和 `ssd/engine/draft_runner.py:38`。因此 README 中的 Llama 70B SSD 命令等价于 target TP=4 加 1 张 draft GPU。
- batch / 序列长度：`bench/bench.py:42-50` 默认 `block_sz=256`、`b=1`、`max_model_len=8192`、`input_len=128`、`output_len=512`、`numseqs=128`。`b` 控制 `max_num_seqs`，不是训练 batch；本仓库没有训练脚本、optimizer、grad accumulation 或 lr schedule。
- 显存规模：KV cache 按当前 GPU free memory 动态分配，默认 `gpu_memory_utilization=0.7`；draft async config 把 draft GPU utilization 提到 0.8。更重要的是，draft async 会先为 tree cache logits 预留显存，代码公式在 `ssd/engine/model_runner.py:464-472`。

文件 `ssd/engine/model_runner.py:464-472`：

```python
reserved_bytes = B * (K + 1) * F * (K + 1) * V * dtype_size
usable_bytes = max(usable_bytes - reserved_bytes, 0)
assert usable_bytes > 0
```

这比论文里“hundreds of MB”更具体：显存随 batch、$(K+1)^2$、fanout 和 vocab size 线性增长。以 README 默认 `B=1,K=7,F=3`、Llama vocab 约 128K、bf16 粗算，仅 logits tree cache 约 $1\times8\times3\times8\times128k\times2 \approx 49$ MB；batch 16 时约 786 MB，还未计 FlashInfer workspace 与 KV pages。
- FlashInfer/CUDA graph 额外内存：`ssd/engine/model_runner.py:159-205` 为 async draft wrapper 分配 512 MB workspace，并按 batch bucket 创建 CUDA graph wrapper；`ssd/engine/helpers/cudagraph_helpers.py:777-902` 为 FI tree decode 捕获不同 batch size 的 graph。
- 与论文声称的算力对照：代码强力支持“single H100 node, target 4xH100 TP, SSD 额外 1xH100 draft”的实验设定；README 也明确 CUDA >= 12.8 且在 H100 测试。报告第 8 节对默认 512 prompts、512 decode tokens、5 张 H100 的描述无需修订。
- 需要注意的 baseline 差异：`bench/run_sglang_bench.py:85-89` 默认 SGLang TP=4、`max-running-requests=1`、standalone SD `num_steps=4,num_draft_tokens=5`；`bench/run_vllm_bench.py:83-86` 默认 vLLM TP=4、`max-num-seqs=1`、`num_speculative_tokens=5`。但 `bench/bench_paths.py:46-53` 对外部 baseline 的 Llama 70B 默认路径是 Llama-3.3-70B-Instruct，不是 native SSD benchmark 的 Llama-3.1-70B；复现实验表时应显式设置 `BENCH_LLAMA_70B` 以匹配论文配置。

### 10.4 可复现性评价

- 综合评价：普通研究者可复现性偏低；若已经有单节点 5 张 H100、CUDA 12.8、Llama/Qwen 权重访问权限和稳定 HuggingFace cache，则可复现性为中。
- 有利因素：仓库给出 MIT license、明确 README 命令、`uv.lock`、模型下载脚本、数据下载/预处理脚本、native SSD benchmark、SGLang/vLLM baseline wrapper、交互式 chat 脚本和可选 wandb logging。代码也固定了 Python 随机种子和 sampler generator seed。
- 主要门槛：没有预训练权重、没有预处理数据、没有 Docker/CI、没有官方 reproduction log；Llama 权重需要 HuggingFace 访问授权，70B/32B target 和 5-GPU SSD 命令对普通实验室很重。SGLang/vLLM baseline 还需要额外 conda 环境。
- 已知坑：`SSD_HF_CACHE` 与 `SSD_DATASET_DIR` 缺失会在 import 阶段报错；`SSD_HF_CACHE` 必须指向 hub 目录而不是 HF_HOME 根目录；README 建议 `python -O`，否则 debug prints/assert 路径会带来明显 overhead；Triton/TorchInductor cache 在网络文件系统上可能出错，bench README 建议设置本地 `TRITON_CACHE_DIR` 与 `TORCHINDUCTOR_CACHE_DIR`。
- 已知坑：数据文件缺失时，`bench/bench_helpers.py:159-163`、`bench/bench_helpers.py:212-219` 会 warning 后回退到 random prompts；如果没有注意日志，可能误以为自己复现了四个真实数据集。复现实验表应检查 `SSD_DATASET_DIR` 下是否真有 `humaneval/`、`alpaca/`、`gsm8k/`、`ultrafeedback/` 的 JSONL。
- 已知坑：bench README 说明 SGLang/vLLM 使用 server API，计时包含 HTTP overhead 和 prefill time；native SSD 的主结果打印同时含 `official_end_to_end_throughput` 和内部 `metrics_decode_throughput`。复现论文 decode-only 表时应优先对齐作者使用的 decode throughput 口径。
- 功能边界：README roadmap 写明 draft data parallel、OpenAI-compatible HTTP serving、新模型/MoE 支持仍是未来工作；因此当前公开代码主要是研究型 single-node inference engine，而不是完整 production serving stack。
