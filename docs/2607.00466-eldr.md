## 2. 核心贡献概述

### 中文概述

在 PD 分离（Prefill-Decode Disaggregated）的 MoE 模型服务中，现有解码路由策略仅平衡各解码 worker 的负载，但忽略了一个关键事实：对于 MoE 模型，负载相同的 worker 延迟可能差异很大，因为每个解码步的延迟由该批次激活的**不重复专家数量**决定，而非 token 数量。本文提出 ELDR，一种专家局部性感知的解码路由策略，通过从 prefill 阶段的专家激活构建专家签名，利用平衡 K-means 离线聚类和在线局部性带路由，将激活相似专家的请求分配到同一解码 worker，从而减少每步加载的专家权重总量，降低解码延迟。ELDR 还设计了与 KV 缓存共索引的签名缓存机制，保持与前缀缓存的一致性。

### 英文摘要（摘自原文）

> In prefill-decode (PD) disaggregated LLM serving, each request is assigned to a decode worker after prefill. Existing decode routers balance only load; for mixture-of-experts (MoE) models this is incomplete: equally loaded workers can differ in latency, since each decode step loads the weights of every distinct expert its batch activates. We present ELDR, an expert-locality-aware decode router for PD-disaggregated MoE serving. From a request's prefill expert activations, ELDR builds an expert signature predicting the experts it will activate during generation. Offline, balanced K-means partitions signature space across decode workers; online, locality-band routing sends each request to the least-loaded worker among those best matching its signature. A signature cache, co-indexed with the KV cache at KV-block granularity, keeps signatures exact under prefix caching. Implemented in vLLM and evaluated on deployments of up to 40 GPUs, ELDR reduces median TPOT by 5.9-13.9% over the strongest of four load-balancing baselines across three MoE models and two workloads, with model outputs unchanged.

## 3. 一句话精髓

在 MoE 模型的 PD 分离服务中，解码延迟取决于批次中激活的不重复专家数量而非请求数量；ELDR 通过从 prefill 阶段提取专家激活签名，将激活相似专家的请求路由到同一解码 worker，从而减少每步需要加载的专家权重，实现无损的延迟降低。

## 4. 学术贡献清单

### 4.1 动机

**核心问题**：PD 分离架构下，MoE 模型的解码延迟由每步激活的不重复专家数量主导，而非传统的 batch size。

![MoE 解码延迟与活跃专家数的关系](sources/2607.00466-eldr-expert-locality-aware/arxiv/figure/03_motivation/moe_latency.pdf)

**关键观察**：
1. **Active Expert Count 驱动 MoE 解码延迟**：在 Qwen3-30B-A3B 上，active experts 从 16 增长到 128 时，MoE 层延迟增加 4.7 倍（batch size 固定为 64）；而 batch size 变化几乎不影响延迟。
2. **专家按领域特化**：不同任务域（Code/Math/Medical/Legal）和语言域（English/Chinese/Russian/French）激活不同的专家子集，同域请求的专家激活高度重叠。
3. **Prefill 预测 Decode 专家激活**：prefill 和 decode 的专家激活相关性达 0.70-0.92，使得在 prefill-decode 交接点可以预测 decode 阶段的专家使用。

**机会量化**：同域批次比混合域批次每步少激活 17-21%（任务域）和 3-10%（语言域）的专家。

**三大挑战**：
1. 设计能准确预测 decode 专家重叠的专家签名
2. 协调局部性与负载均衡两个目标
3. 在前缀缓存命中时保持签名完整性

### 4.2 方法创新

**三大创新点**：

1. **Expert Locality 作为可预测的路由维度**
   - 从 prefill 专家激活构建 expert signature
   - 用 Spearman 秩相关衡量签名质量：$\rho = \mathrm{Spearman}(\mathrm{cos\text{-}dist}(s_i, s_j), \mathrm{cos\text{-}dist}(p_i, p_j))$
   - 签名设计三原则：离散计数优于连续分数、IDF 降噪通用专家、保留信息量最大的层

2. **Expert-Locality-Aware Decode Routing**
   - 离线：Hungarian-balanced K-means 聚类，每个解码 worker 一个质心
   - 在线：Locality-band routing，参数 $\tau=0.1$，在局部性带内选择负载最低的 worker

3. **Prefix-Cache-Coherent Signatures**
   - 签名缓存与 KV 缓存共索引（block 粒度）
   - 请求签名 = 其 KV block 集合的签名之和
   - 自动处理部分命中、完全命中、驱逐等场景

### 4.3 实验结论

**主实验**（8P16D 拓扑）：
- **任务域**：ELDR 比最佳负载均衡基线降低中位 TPOT 7.0-13.9%，尾部 TPOT 3.4-6.0%
- **语言域**：ELDR 比最佳负载均衡基线降低中位 TPOT 5.9-10.0%
- ELDR 在所有请求速率下均优于所有基线

**与 Domain 基线对比**：
- 任务域：ELDR 比 Domain 降低中位 TPOT 1.4-6.9%（Domain 用 4 个硬标签，ELDR 用 K=16 个签名聚类）
- 语言域：Domain 崩溃，ELDR 比 Domain 降低中位 TPOT 5.7-9.1%

**消融实验**：
- 离散 count·idf 签名比连续 gate-prob 平均多降 3pp TPOT P50
- Hungarian-balanced K-means 比 vanilla K-means：vanilla 回退尾部 TPOT 17.4%，balanced 同时改善 P50 和 P99
- τ=0.1 最优：纯 top-1 (τ=0) 回退尾部，τ>0.1 中位收益递减
- 前缀缓存与 ELDR 的收益可叠加

**泛化实验**：
- 拓扑泛化：8P8D → 8P16D → 8P24D，中位 TPOT 改善单调增长（8.0% → 9.8% → 10.2%）
- 大模型泛化：Qwen3-235B-A22B（40 GPU，TP=4，EP=4），中位 TPOT 降低 2.7-4.3%

**开销**：
- 每请求 0.86ms（占中位 TTFT 1.2%）
- 签名缓存 < KV 缓存的 1%
- 校准：1000 条 prompt 耗时 4-15 分钟；离线拟合 < 10 秒

## 7. 批判性分析

### 7.1 与前作关系

**ELDR 的定位**：在 MoE 服务优化的研究图谱中，ELDR 填补了一个独特的空白——**跨 decode worker 的无损专家局部性路由**。

| 维度 | EPLB / MoETuner | EA Patterns / Semantic Parallelism | Lynx / XShare / Opportunistic | **ELDR** |
|------|----------------|-----------------------------------|-------------------------------|----------|
| 平衡粒度 | intra-worker (EP rank 间) | inter-node 通信 | intra-batch expert 选择 | **inter-worker (decode worker 间)** |
| 是否改变专家选择 | 否 | 否 | **是（有损）** | **否（无损）** |
| 目标瓶颈 | EP rank 负载 | all-to-all 通信 | 解码带宽 | **解码带宽** |

**与 EA Patterns (2604.23150) 的关系**：两者都观察到专家激活模式的领域特化，但目标不同。EA Patterns 用激活模式优化 EP rank 间的 expert-to-GPU 映射以减少通信；ELDR 用激活模式优化请求到 decode worker 的分配以减少每步加载的专家数。两者正交，可组合使用。

**与 Lynx (2411.08982) 的关系**：Lynx 通过动态丢弃低重要性专家来减少解码带宽，但有精度损失。ELDR 是无损的——它不改变任何 token 的专家选择，只改变请求由哪个 worker 服务。

### 7.2 局限性

1. **校准依赖**：需要 1000 条 prompt 的校准数据（4-15 分钟），且假设校准数据分布与服务时分布一致。论文未讨论分布漂移时的行为。

2. **静态 τ**：局部性带宽 τ=0.1 贯穿所有实验，未展示其对不同负载模式的适应性。虽然消融了 τ ∈ {0, 0.1, 0.2, 0.3}，但未探索自适应 τ。

3. **单次离线拟合**：论文明确说"use a single offline fit in this work"，未探索在线增量更新签名聚类的方案。在长时间运行中，工作负载可能漂移。

4. **语言域改善较任务域小**：语言域的改善（5.9-10.0%）显著小于任务域（7.0-13.9%），且尾部 TPOT 在 GPT-OSS 和 Gemma 上略有回退。这表明专家局部性在领域边界清晰时更有效。

5. **未评估训练场景**：仅针对推理服务，未讨论是否可用于训练时的 MoE 负载均衡。

6. **硬件单一性**：所有实验在 AMD MI300X 上进行，未验证在 NVIDIA GPU 上的表现。

7. **签名缓存的 GPU 显存开销**：虽然声称 <1% KV 缓存，但在显存极度紧张的部署中（如长上下文场景），额外的 per-block 签名存储仍需考虑。

## 8. 方法细节

**系统总览**：

![ELDR 系统总览](sources/2607.00466-eldr-expert-locality-aware/arxiv/figure/04_design/fig_overview.pdf)

### 8.1 Expert Signature 构建

**目标**：将请求 $r$ 的 prefill 专家激活压缩为向量 $s_r$，使得签名空间中的距离反映 decode 阶段的专家重叠程度。

**质量度量**：
$$\rho = \mathrm{Spearman}(\mathrm{cos\text{-}dist}(s_i, s_j), \mathrm{cos\text{-}dist}(p_i, p_j))$$
其中 $p_i(\ell, e) \in [0,1]$ 是请求 $i$ 在 decode 阶段在层 $\ell$ 选择专家 $e$ 的概率。

**构建步骤**：
1. **计数**：prefill 时统计每层每个专家接收的 token 数 $c_r(\ell) \in \mathbb{N}^E$
2. **IDF 降噪**：$\tilde{c}_r(\ell, e) = c_r(\ell, e) \cdot \log\frac{|\mathcal{C}|+1}{\mathrm{df}(\ell, e)+1}$，其中 $\mathrm{df}(\ell, e)$ 是校准集中专家 $e$ 在层 $\ell$ 至少被选中一次的请求数
3. **层选择**：贪心层选择算法，从空集开始，每步添加使累积 $\rho$ 增加最多的层，保留前 $N^*$ 层
4. **归一化**：$s_r = x_r / \|x_r\|_2$

**签名变换对比**：

![不同签名变换的 Spearman 相关性](sources/2607.00466-eldr-expert-locality-aware/arxiv/figure/04_design/sig_transform.pdf)

**层选择效果**：

![层数与签名质量的关系](sources/2607.00466-eldr-expert-locality-aware/arxiv/figure/04_design/sig_layers.pdf)

**设计验证**（Fig. 4）：六种候选变换中，count·idf 的平均 $\rho$ 最高，比连续 gate-prob 高 0.035+。

### 8.2 离线聚类：Hungarian-balanced K-means

**目标**：将校准签名聚为 $K$ 类（$K$ = 解码 worker 数），每类大小相等且内部签名相似。

**算法**：在标准 K-means 的分配阶段，用 Hungarian 算法求解全局最优分配，约束每个质心最多分配 $\lceil N/K \rceil$ 个点。

**输出**：$K$ 个单位质心，每个对应一个解码 worker。

**复杂度**：$O(n^3)$，但 $n=1000$（校准集大小），实际 <10 秒。

### 8.3 在线路由：Locality-band Routing

**算法**：
1. 计算请求签名与 $K$ 个质心的余弦相似度
2. 找到最高相似度 $s^* = \max_k s_k$
3. 在相似度 $\ge s^* - \tau$ 的 worker 中，选择当前负载最低的

**参数**：$\tau=0.1$，在纯 top-1（$\tau=0$）和纯 JSQ（$\tau=1$）之间平衡。

**自适应性**：签名置信度高时，局部性带窄（few workers in band）；签名模糊时，带宽扩大（more workers in band）。

### 8.4 Prefix Cache 一致性

**签名与 KV 缓存的共索引关系**：

![Prefix Cache 签名一致性](sources/2607.00466-eldr-expert-locality-aware/arxiv/figure/04_design/fig_prefix_coherence.pdf)

**机制**：
- 每个 KV block 对应一行签名向量（per-layer per-expert 计数，int8）
- 请求签名 = 其 KV block 集合的签名之和：$s_r = \sum_{b \in \mathcal{B}(r)} \mathrm{sig}[b]$
- 签名缓存与 KV 缓存共索引、共生命周期

**存储**：$\text{num\_gpu\_blocks} \cdot L \cdot E$ 字节，每个 block 最多 6 KiB。

### 8.5 算力与资源

- **硬件**：5 节点 × 8 AMD MI300X GPU（192 GB HBM），400 Gbps NDR InfiniBand
- **最大部署**：40 GPU（Qwen3-235B-A22B，TP=4，EP=4）
- **校准开销**：1000 条 prompt，4-15 分钟/（模型，数据集）
- **离线拟合**：<10 秒（CPU）
- **运行时开销**：0.86ms/请求（占 TTFT 1.2%），其中 signature capture 0.48ms + D2H 0.21ms + routing 0.15ms

## 9. 实验

### 9.1 硬件与软件

- **集群**：5 节点 AMD MI300X（8 GPU/节点，192 GB HBM），400 Gbps NDR InfiniBand
- **软件**：vLLM 0.21.0rc1 / ROCm 7.2，NIXL 连接器
- **代码量**：约 2000 行 Python

### 9.2 模型

| 模型 | 参数量 | Experts | Top-k | 精度 | TP/EP |
|------|--------|---------|-------|------|-------|
| Qwen3-30B-A3B | 30B (3B active) | 128 | 8 | bf16 | TP=1 |
| GPT-OSS-120B | 120B | 128 | 4 | mxfp4 | TP=1 |
| Gemma-4-26B-A4B | 26B (4B active) | 128 | 8 | bf16 | TP=1 |
| Qwen3-235B-A22B | 235B (22B active) | 128 | 8 | bf16 | TP=4, EP=4 |

### 9.3 数据集

- **Task**：11,668 条 prompt，4 个领域——Legal (3600), Code (2779), Math (2744), Medical (2545)
- **Language**：14,000 条 WildChat 子集，English/Chinese/Russian/French 占 87.6%
- 每个数据集的 1000 条校准子集与评估集不重叠

### 9.4 基线

- **Random**：随机分配 decode worker
- **Round-Robin (RR)**：轮询
- **Join-Shortest-Queue (JSQ)**：最短队列
- **Power-of-Two-Choices (P2C)**：随机选两个，取负载低的
- **Domain**：按 oracle 域标签分配 decoder，域内 JSQ 负载均衡
