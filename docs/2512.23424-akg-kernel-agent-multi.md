# AKG kernel Agent: A Multi-Agent Framework for Cross-Platform Kernel Synthesis

## 1. 基本情况

这篇论文提出 **AKG kernel agent**，全称为 **AI-driven Kernel Generator**，目标是用 LLM 驱动的 multi-agent system 自动完成高性能计算 kernel 的生成、迁移与调优。论文背景是：现代 AI 模型，尤其是 LLM、多模态模型和推荐系统，越来越依赖大量定制化高性能算子；同时 sparsity、quantization、fusion、动态 shape 以及硬件平台快速迭代，使手工 kernel 优化难以跟上模型和硬件演化速度。

论文的核心定位不是提出某个单一 kernel 优化算法，而是提出一个面向多 DSL、多硬件后端的自动 kernel synthesis 框架。它支持的目标 DSL / 语言包括论文中明确提到的 **Triton、TileLang、CPP、CUDA-C、AscendC** 等，目标后端包括 **GPU、NPU、CPU**，并支持 PyTorch、MindSpore、NumPy 等 frontend reference implementation。

从个人知识库角度看，这篇论文可归入 **LLM Serving** 或更宽泛的 **AI Systems / AI Infra** 方向。它不是 serving runtime 本身，而是服务于 LLM Serving 体系中的高性能算子生成与移植，因此 `line_role` 更适合标为 **tooling**。它与 Triton、TVM、FlashAttention、KernelBench、AutoTriton、KernelLLM、Kevin、QiMeng-Kernel 等工作处于同一技术语境：如何自动化生成正确且高性能的硬件 kernel。

论文宣称在 **KernelBench** 上使用 Triton DSL、跨 GPU 和 NPU backend 评估时，AKG kernel agent 相比 PyTorch Eager baseline 实现获得平均 **1.46$\times$ speedup**。在论文 introduction 末尾还提到，系统在 KernelBench Level 1 上可达最高 **100% correctness**，在作者自建、更困难且包含 dynamic shapes 的 benchmark 上达到 **85--91% correctness**，并能生成匹配或超过 PyTorch Eager 的 kernel。

需要注意：用户提供的 TeX 主文件内容在 Methodology 的 `Iterative Search-Based Optimization` 算法部分被截断，未包含完整实验表格、附录和 bibliography。因此本报告对实验细节的复原主要依据摘要和 introduction 中的结果描述，不额外编造未给出的表格数值。

## 2. 核心贡献概述

本文的贡献可以概括为：**把 LLM kernel generation 从“单模型直接写代码”改造成“带中间表示、文档注入、检索增强、验证反馈和性能搜索”的 multi-agent 工程系统**。

具体而言，AKG kernel agent 的核心由四类 agent 组成：

1. **Designer**：分析 operator specification 和硬件特性，生成一个 DSL-agnostic 的 **Unified Sketch**。
2. **Coder**：把 Unified Sketch 翻译为目标 DSL 的可执行 kernel 代码。
3. **Verifier**：负责编译、数值正确性验证和性能 profiling。
4. **Conductor**：作为 orchestrator，根据 Verifier 反馈判断错误类型，并把任务路由回 Coder 或 Designer。

这套设计的关键思想是解耦两件事：

- **优化策略设计**：如何 tile、parallelize、reuse memory、组织 reduction、利用 cache / shared memory / registers / NPU core。
- **目标 DSL 实现**：如何用 Triton、CUDA-C、TileLang、AscendC 等具体语法表达上述策略。

论文认为，直接让 LLM 从 PyTorch reference implementation 一步生成高性能 kernel，容易把算法理解、硬件优化和 DSL 语法混在一起，导致 compile error、numerical mismatch 或性能很差。AKG 通过 Unified Sketch 将优化 intent 先显式表达出来，再由 Coder 结合文档和案例完成落地。

此外，论文提出 **Document-Driven Integration, DDI**，把硬件手册、DSL API reference、专家优化经验、常见坑、示例代码组织成标准化文档，让 agent 在 runtime 消费这些知识。这样，系统可以通过接入新文档快速支持新 DSL 或新硬件，而不是修改 agent 主逻辑。

最后，系统加入 **Hierarchical Code Retrieval** 和 **Iterative Search-Based Optimization**。前者用于从数据库中找到语义、DSL/backend、shape 都相近的已有 kernel 示例；后者通过多轮并行生成、验证、profiling、对比分析和 island model 搜索更优 kernel。

## 3. 一句话精髓（写给外行）

这篇论文想做一个“会读硬件说明书、会拆任务、会写代码、会跑测试、会反复调优”的 AI 程序员团队，自动把普通的 PyTorch 算子改写成适配不同芯片的高性能 kernel。

## 4. 学术贡献清单

### 4.1 Multi-agent kernel generation architecture

论文提出由 Designer、Coder、Verifier、Conductor 构成的 multi-agent workflow。相比单个 LLM prompt 直接生成 kernel，这种架构有三个优点：

- 将高层优化策略和底层代码生成拆开；
- 将错误处理显式建模为状态路由问题；
- 允许在每个阶段注入不同类型知识，例如硬件文档、DSL API、历史示例、错误日志。

其中 **Conductor** 是系统闭环的关键。它不是固定把所有失败都送回同一个 agent，而是根据错误类型做 adaptive routing：

- syntax error、API misuse、runtime error 更可能送回 **Coder**；
- algorithm error、memory pattern error、parallelization 结构错误更可能送回 **Designer**。

论文给出的 Conductor 伪代码如下：

1. 若 Verifier 成功，则结束；
2. 否则根据日志分类错误；
3. 用 LLM 结合历史状态分析 root cause；
4. 根据错误类型返回下一个 agent 和修复建议。

### 4.2 Unified Sketch：可迁移的优化意图中间表示

论文提出 **Unified Sketch** 作为 Designer 与 Coder 之间的中间层。它不是传统 compiler IR，而是面向 LLM 理解和生成的 minimalist DSL。形式化定义为：

$$
\mathcal{S} = (\mathcal{D}, \mathcal{O}, \mathcal{C}, \mathcal{H})
$$

其中：

- $\mathcal{D}$：declarations，包括 symbols、tensors、constexpr；
- $\mathcal{O}$：core operations，包括 `alloc`、`load`、`store` 和标准 compute 函数；
- $\mathcal{C}$：control flow，用 Python 风格 `for` / `range` 表达 tiling 和 loop nest；
- $\mathcal{H}$：optimization hints，用 `@llm_hint` 表示 parallelization、pipeline、vectorize、unroll 等意图。

Unified Sketch 的重要性在于，它使用硬件无关的语义 hint。例如：

- `"fastest"` 可对应 GPU register；
- `"fast"` 可对应 shared memory / L1；
- `"coreidx"` 可对应 NPU core parallelism；
- `"grididx"` / `"threadidx"` 可对应 GPU execution hierarchy。

这让同一个 sketch 理论上可以被翻译到 GPU、NPU 或 CPU 后端。

### 4.3 Document-Driven Integration

论文把 documentation 视为系统扩展接口。DocSpec 包含四类文档：

1. **basic documentation**：核心概念、语法、执行模型；
2. **API documentation**：接口签名和使用模式；
3. **expert suggestions**：优化建议和常见错误；
4. **reference examples**：按 frontend / DSL / backend 组织的工作样例。

这种机制解决的是 kernel generation 中的一个实际问题：硬件和 DSL 太多，不能为每个组合硬编码支持逻辑。DDI 的主张是：只要能把新 target 的知识写进标准文档，agent 就能在 runtime 读取并使用。

论文还提到对长文档做动态选择和 LLM-based compression：例如生成 reduction kernel 时优先加载 reduction primitives、shared memory 相关文档，而不是把整个 API reference 都塞进 prompt。

### 4.4 Hierarchical Code Retrieval

论文指出，普通 RAG 在 kernel retrieval 中有局限：代码表面相似不代表语义或 shape pattern 相近；语义相近的优化策略也可能语法上差异很大。因此它提出分层检索：

1. 用 LLM 从 query operator 中抽取 task features；
2. 对 computation logic 做 embedding semantic search；
3. 对 DSL、backend、operator type 做 hard filtering；
4. 对 shape compatibility 做 semantic matching；
5. 返回 top-$k$ 示例给 Coder。

第一阶段候选集形式为：

$$
\mathcal{C}_1 = \{ x \in \mathcal{DB} \mid \cos(\mathbf{e}_q, \mathbf{e}_x) > \tau \}
$$

其中 cosine similarity 为：

$$
\cos(\mathbf{u}, \mathbf{v}) =
\frac{\mathbf{u} \cdot \mathbf{v}}{\|\mathbf{u}\| \|\mathbf{v}\|}
$$

shape 匹配分数为：

$$
\text{score}(q, x) =
\cos(\mathbf{e}_q^{\text{shape}}, \mathbf{e}_x^{\text{shape}})
$$

这一设计让 Coder 获得更贴近目标后端、目标 DSL 和目标 shape 的样例，从而降低 API misuse 和错误边界处理的概率。

### 4.5 Iterative Search-Based Optimization

论文把性能调优建模为搜索问题：

$$
I^* = \arg\min_{I \in \mathcal{I}(O)} T(I, H)
$$

其中 $\mathcal{I}(O)$ 是 operator $O$ 的有效实现空间，$T(I,H)$ 是实现 $I$ 在硬件 $H$ 上的执行时间。

AKG 不是只生成一个 kernel，而是多轮并行生成多个候选，实现如下闭环：

1. 生成初始候选 population；
2. 编译、验证和 profile；
3. 对 high-performing 和 low-performing 实现做 LLM comparative analysis；
4. 识别有效 tiling、memory pattern、parallelization choices；
5. 形成下一轮优化计划；
6. 继续生成新候选。

论文还引入 **island model**，把候选 population 划分成多个半独立 island，周期性迁移 elite implementations：

$$
\text{Island}_i.\text{population}
\leftarrow
\text{Island}_i.\text{population}
\cup
\text{Elite}(\text{Island}_{i-1})
$$

这可以在探索多样性和传播优秀策略之间取得平衡。

## 5. 写作故事线

论文的叙事结构比较典型，按“问题—现有方法不足—系统设计—评估”的路线展开。

### 5.1 问题引入：AI 模型越来越依赖高性能 kernel

Introduction 首先强调：AI 模型性能高度依赖底层 computational kernels。随着 LLM、多模态模型、推荐系统变复杂，以及 sparsity、quantization、fusion 等技术普及，算子形态变得更细碎、更定制化。与此同时，硬件平台快速变化，开发者需要为不同 GPU、NPU、CPU 架构写不同版本 kernel。

手工优化需要同时懂算法和硬件，例如 memory hierarchy、parallel execution model、instruction set、thread block size、memory access pattern 等。这种优化高度专业、重复且不可扩展。论文用 FlashAttention 的演进作为例子：即使是影响力很大的 kernel，对新架构的优化也常常滞后。

### 5.2 现有 LLM 方案的不足

论文接着讨论 LLM code generation 的机会。GPT-4、DeepSeek-R1 等模型已经能生成较复杂代码，因此 kernel generation 也成为可能。但现有方法有两个主流方向：

- 用 general-purpose LLM + prompting；
- fine-tune specialized kernel model。

论文认为二者都存在不足：

- general-purpose LLM 容易生成编译错误、数值错误或低性能代码；
- fine-tuned models 受限于高质量 kernel 数据稀缺，泛化到多 operator、多 hardware、多 DSL 时困难。

KernelBench、MultiKernelBench、TritonBench 等 benchmark 暴露了这些问题。

### 5.3 核心转折：不是更强的单模型，而是结构化 agent 系统

本文的关键转折是：不要让一个 LLM 一次性解决所有问题，而是用多 agent 拆分问题。Designer 负责策略，Coder 负责实现，Verifier 负责客观检测，Conductor 负责流程控制和错误归因。

这个写作选择让论文从“LLM 能不能写 kernel”转向“如何组织 LLM、文档、检索、编译器和 profiler 形成可扩展系统”。

### 5.4 泛化问题：用文档驱动而不是硬编码

然后论文提出 Document-Driven Integration，以回应跨平台泛化问题。因为新 DSL、新硬件、新 API 不断出现，框架不能依赖固定代码逻辑。把 documentation 标准化为 agent 的输入，是论文认为系统可扩展的关键。

### 5.5 性能问题：正确还不够，还要搜索调优

最后论文承认，能生成正确 kernel 不代表性能好。因此引入 iterative search、parallel candidate generation、comparative analysis 和 island model，通过多轮 profiler feedback 寻找更快实现。

整体故事线可以简化为：

> 手写 kernel 不可扩展；单 LLM 生成 kernel 不可靠；所以需要一个能读文档、检索样例、拆分任务、验证反馈、反复搜索的 multi-agent kernel generation system。

## 7. 批判性分析

### 7.1 优点：系统设计贴近 kernel 工程现实

本文的最大优点是没有把问题简化为“让 LLM 直接写 Triton”。真实 kernel 工程中，困难来自多个层次：

- 算子语义理解；
- shape / dtype / layout 适配；
- tiling 与 parallelization；
- memory hierarchy 利用；
- DSL API 细节；
- 编译错误和 runtime error；
- numerical tolerance；
- profiling 与性能回归。

AKG 的 multi-agent decomposition 正好对应这些工程子问题。尤其是 Verifier + Conductor 的闭环，让系统能够利用编译器和 profiler 的客观反馈，而不是只依赖 LLM 自评。

### 7.2 优点：Unified Sketch 是合理的抽象层

Unified Sketch 的价值在于，它比自然语言设计说明更结构化，又比真实 DSL 更抽象。对 LLM 来说，它降低了语法负担；对跨平台迁移来说，它保留了优化意图。

例如 `alloc(..., llm_hint=["fast", "accumulator"])` 这样的表达，不绑定 CUDA shared memory、NPU local memory 或 CPU cache，而是表达“这里需要较快存储、作为累加器使用”的意图。这种 abstraction 对多 backend generation 是有意义的。

不过，Unified Sketch 是否足以表达复杂 kernel 优化仍需更多证据。例如：

- tensor core / mma 指令级优化；
- warp-level primitives；
- bank conflict avoidance；
- asynchronous copy / double buffering；
- inter-block synchronization；
- complex layout transformation；
- sparse / quantized kernel 的 bit-level packing。

主文件中给出的 RMSNorm sketch 较清晰，但不代表它能覆盖所有高性能 kernel 细节。

### 7.3 优点：Document-Driven Integration 抓住了可维护性痛点

LLM agent 系统最大的问题之一是知识更新。硬件手册和 DSL API 持续变化，如果知识固化在 prompt template 或代码逻辑中，很快会过时。DDI 把新 target 支持转化为文档准备任务，这对工业环境更现实。

但 DDI 的质量依赖文档质量。论文提到有 automated documentation formatting tool，但 TeX 截断内容中没有看到这个工具的详细评估，例如：

- 文档格式错误时系统如何鲁棒处理？
- LLM compression 是否会丢掉关键 API 约束？
- expert suggestions 的质量如何度量？
- 不同文档规模对 prompt cost 和 correctness 的影响如何？

这些是系统落地时的关键问题。

### 7.4 风险：性能 claim 需要更完整实验支持

摘要给出平均 1.46$\times$ speedup，introduction 提到 KernelBench Level 1 correctness 最高 100%，自建 benchmark 85--91%。这些结果有吸引力，但由于提供的 TeX 内容未包含完整实验章节和表格，因此目前无法核查：

- baseline 具体有哪些；
- 是否与 AutoTriton、KernelLLM、Kevin、QiMeng-Kernel 等直接比较；
- 1.46$\times$ 是 arithmetic mean、geometric mean 还是按任务平均；
- 失败样本如何计入 speedup；
- NPU 上 Triton 支持的具体实现方式；
- benchmark 中 static vs dynamic shape 的比例；
- profiling 是否包含 compile time；
- generated kernel 与 PyTorch Eager 的公平性，例如是否比较 eager unfused baseline 而非 torch.compile / vendor library。

论文 introduction 中提到 “up to 1.46$\times$ geometric mean speedup”，摘要中则说 “average speedup of 1.46$\times$”。如果完整论文没有进一步澄清，读者需要警惕平均方式差异。

### 7.5 风险：LLM agent 成本与稳定性未在已给内容中充分展开

Multi-agent + RAG + 多轮搜索通常会带来较高成本：

- 多次 LLM call；
- 多候选代码编译；
- 多轮 profiling；
- 文档检索和压缩；
- Conductor 的错误分析；
- island model 的并行探索。

对于离线 kernel 库构建，这些成本可以接受；但如果希望在模型部署时即时生成 kernel，则 latency 和资源成本可能不可忽略。已给内容中没有看到对 end-to-end generation time、token cost、compile cost、profiling budget 的完整报告。

### 7.6 风险：benchmark reward hacking 的修正需要具体机制

论文声称自建 benchmark 修正了 KernelBench 中的 reward-hacking vulnerabilities，并包含 fused operators 和 dynamic shapes。这是一个重要贡献点，但 TeX 截断部分未显示 benchmark 具体设计。理想情况下需要说明：

- reward hacking 的具体形式是什么；
- 如何防止 hard-code output、shape-specific hack 或 baseline exploit；
- dynamic shape 测试如何采样；
- correctness threshold 是否足以覆盖数值稳定性；
- 是否有 hidden tests。

没有这些细节时，这一贡献还停留在声明层面。

## 8. 方法细节

### 8.1 输入与输出

系统输入通常是一个 operator specification，可能以 PyTorch、MindSpore 或 NumPy reference implementation 表达。系统还接收目标硬件和目标 DSL 信息，例如：

- frontend：PyTorch / MindSpore / NumPy；
- DSL：Triton / TileLang / CUDA-C / AscendC / CPP；
- backend：CUDA GPU / Ascend NPU / CPU；
- operator shape、dtype、layout、dynamic shape 约束。

系统输出是完整 kernel implementation，包括：

- device-side kernel function；
- host-side wrapper；
- 与 frontend 对接的调用逻辑；
- 可能的 autotuned parameters 或 constexpr。

### 8.2 Designer：从 operator 到 Unified Sketch

Designer 的任务是理解计算语义并生成优化计划。论文强调它会考虑：

1. computation inherent parallelism；
2. memory bandwidth constraints；
3. data reuse opportunity；
4. hardware-specific feature，例如 tensor cores、vector units；
5. previous failed attempts 的反馈。

Unified Sketch 的四个组成部分为：

$$
\mathcal{S} = (\mathcal{D}, \mathcal{O}, \mathcal{C}, \mathcal{H})
$$

其中 $\mathcal{D}$ 声明符号和 tensor，$\mathcal{O}$ 表示核心操作，$\mathcal{C}$ 表示 loop / tiling 结构，$\mathcal{H}$ 表示 optimization hints。

论文给出的 RMSNorm sketch 示例展示了两阶段计算：

1. 第一遍遍历 $F$ 维，计算 square sum；
2. 计算 mean、加 epsilon、sqrt 得到 RMS；
3. 第二遍重新加载输入并归一化；
4. 按 batch 和 $D1$ tile 并行。

这个 sketch 中的关键 hint 包括：

- `@llm_hint("parallel", "coreidx")`：指示并行映射到 core；
- `@llm_hint("pipeline")`：指示 pipeline；
- `alloc(..., ["fast", "accumulator", "init_zero"])`：指示快速 memory 上的累加 buffer；
- `alloc(..., ["fastest", "temp_workspace"])`：指示临时 workspace 可能放在最快层级。

### 8.3 Coder：从 Unified Sketch 到目标 DSL 代码

Coder 的输入包括：

- Unified Sketch；
- target DSL specifications；
- API documentation；
- retrieved examples；
- previous error logs 和 Conductor suggestions；
- frontend-specific templates。

Coder 的主要工作是：

1. 解析 sketch 中的 tiling、memory、parallelization 决策；
2. 查阅目标 DSL API；
3. 参考相似示例；
4. 生成 kernel 和 wrapper；
5. 根据 Verifier 的错误反馈迭代修复。

这部分的关键并不是 LLM 单纯“翻译”，而是把 sketch、文档、示例和错误日志合并为上下文，生成符合目标 DSL idiom 的代码。

### 8.4 Verifier：正确性和性能门禁

Verifier 负责三件事：

1. compilation；
2. numerical correctness；
3. performance profiling。

数值误差定义为：

$$
e_i =
\begin{cases}
\frac{|y_i^{gen} - y_i^{ref}|}{|y_i^{ref}|} & \text{if } |y_i^{ref}| > \epsilon \\
|y_i^{gen} - y_i^{ref}| & \text{otherwise}
\end{cases}
$$

通过条件为：

$$
\frac{|\{i : e_i > \tau\}|}{N} \leq \tau
$$

这里 $\tau$ 是与 dtype 相关的阈值。这个定义同时考虑相对误差和接近零时的绝对误差。

代码生成 correctness 使用 pass@k：

$$
\text{pass@}k =
\frac{1}{N}
\sum_{i=1}^{N}
\left(
1 -
\frac{\binom{n-c_i}{k}}{\binom{n}{k}}
\right)
$$

其中 $N$ 是任务数，$n$ 是每个任务生成样本数，$c_i$ 是第 $i$ 个任务正确样本数。

性能 speedup 定义为：

$$
\text{Speedup} =
\frac{T_{base}}{T_{gen}}
$$

同时定义：

$$
\text{fast}_p =
\frac{1}{N}
\sum_{i=1}^{N}
\mathbbm{1}[\text{Speedup}_i \geq p]
$$

即 speedup 至少达到 $p$ 的任务比例。

### 8.5 Conductor：错误分析与动态路由

Conductor 维护完整 execution history，并根据 Verifier 返回的结果做错误分类。论文列举的错误类别包括：

- Syntax；
- ApiMisuse；
- Runtime；
- Algorithm；
- MemoryPattern。

路由规则大致为：

- syntax / API / runtime 问题：返回 Coder；
- algorithm / memory pattern 问题：返回 Designer；
- 成功：结束。

这相当于把 kernel generation 变成一个状态机，而不是固定 pipeline。

### 8.6 Document-Driven Integration

DDI 的核心流程可以理解为：

1. 用户准备符合 DocSpec 的文档；
2. 系统格式化和索引这些文档；
3. agent 根据当前任务动态加载相关片段；
4. 长 API 文档经 LLM compression 提取相关接口；
5. expert suggestions 进入 Coder 和 Conductor 的 prompt；
6. examples 进入 hierarchical retrieval。

这套机制使新 DSL / backend 的支持从“改代码”变为“加文档”。

### 8.7 Hierarchical Retrieval

检索流程：

1. LLM 抽取 query operator 的 task features；
2. 计算 feature embedding；
3. 从数据库中按 computation logic 做 semantic search；
4. 对 DSL、backend 做 exact filter；
5. 对 shape 做 compatibility ranking；
6. 返回 top-$k$ examples。

这种机制比单纯代码 embedding 更适合 kernel，因为 kernel 的性能和正确性高度依赖 shape、layout 和硬件后端。

### 8.8 Iterative Search

搜索流程包括：

- 初始生成多个候选；
- 每个候选经过 Verifier；
- 收集成功和失败样本；
- 对高性能与低性能代码做 contrastive analysis；
- 制定下一轮优化计划；
- 使用 island model 保持多样性；
- 将成功实现、sketch 和分析结果写入数据库，供未来 RAG 使用。

这一点使系统具备“经验积累”能力：它不仅为当前 operator 找 kernel，也在构建后续任务可复用的 kernel knowledge base。

## 9. 实验

### 9.1 评估对象

根据摘要和 introduction，论文评估 AKG kernel agent 的主要对象包括：

- **KernelBench**；
- 作者自建 benchmark；
- 多个 DSL-backend 组合；
- Triton DSL 在 GPU 和 NPU 后端上的表现；
- fused operators，覆盖 LLM、computer vision、recommendation models；
- static 和 dynamic input shapes。

论文强调自建 benchmark 的特点是：

1. 包含实际模型中常见的 fused operators；
2. 同时包含 static shapes 和 dynamic shapes；
3. 修正已有 benchmark 中 reward-hacking 漏洞；
4. 更贴近真实生产环境。

### 9.2 Baseline

明确出现的 baseline 是 **PyTorch Eager baseline implementations**。摘要中称 AKG 在 KernelBench 上相对 PyTorch Eager 获得平均 **1.46$\times$ speedup**。

Introduction 中还提到与已有方法的语境相关，包括 KernelLLM、Kevin-32B、AutoTriton、QiMeng 等，但在提供的 TeX 片段中未看到完整对比实验表。因此不能断言论文实际做了与这些方法的逐项数值比较。

### 9.3 Correctness 指标

论文采用 pass@k 和基于 element-wise error 的 correctness verification。Introduction 中给出结果：

- 在 KernelBench Level 1 上，AKG kernel agent 最高达到 **100% correctness**；
- 在作者更困难、包含 dynamic shapes 的 benchmark 上达到 **85--91% correctness**。

这里 “85--91%” 很可能对应不同 DSL-backend 或不同设置，但由于表格缺失，不能进一步展开。

### 9.4 性能指标

性能通过 profiling 后的 execution time 计算：

$$
\text{Speedup} = \frac{T_{base}}{T_{gen}}
$$

论文声称：

- 在 KernelBench 上，使用 Triton DSL、跨 GPU 和 NPU backend，平均 speedup 为 **1.46$\times$**；
- introduction 还提到生成 kernel 能 match or exceed PyTorch Eager performance；
- 使用 iterative search-based tuning 可进一步提升性能。

需要注意，PyTorch Eager 往往不是最强 baseline。对于许多 kernel，torch.compile、vendor library、hand-written Triton/CUDA 或 fused implementation 可能显著强于 eager。因此 1.46$\times$ 说明系统能自动超过普通 eager reference，但不一定说明达到专家手写 kernel 水平。

### 9.5 Ablation 期待点

在已给 TeX 片段中没有看到完整 ablation，但根据方法设计，合理的 ablation 应包括：

- without Unified Sketch；
- without document-driven integration；
- without hierarchical retrieval；
- without Conductor adaptive routing；
- without iterative search；
- fixed pipeline vs adaptive routing；
- ordinary RAG vs hierarchical retrieval；
- single candidate vs parallel candidates；
- static shape vs dynamic shape。

如果完整论文中有这些实验，它们对证明系统各模块必要性很关键。仅有整体 speedup 不足以说明 multi-agent、DDI、RAG 和 search 分别贡献多少。

### 9.6 实验可信度小结

从已给文本看，实验 claim 方向合理，但读者需要在完整 PDF 中重点核查：

1. benchmark task 数量；
2. operator 类型分布；
3. hardware 具体型号；
4. DSL-backend 组合；
5. LLM backbone；
6. generation budget；
7. compilation / profiling 设置；
8. failed samples 如何处理；
9. 与 torch.compile / vendor optimized kernel 的比较；
10. dynamic shape 测试是否为 hidden / held-out。
